Ultrasonic anomaly detector on an ESP32

A cheap HC-SR04 distance sensor, a signal-cleaning pipeline and a 118-parameter autoencoder that runs in pure C++ on the microcontroller: no TensorFlow runtime, no heap. This page runs the same pipeline with the same trained weights in your browser, so you can watch every step work. It also explains how each part of the project was built.

      Hardware

      An ESP32 dev board, an HC-SR04 ultrasonic sensor and two resistors. The sensor sends a 40 kHz ping and holds ECHO high for the round-trip time: distance = echo µs × 0.01715 cm (343 m/s ÷ 2).

      HC-SR04ESP32Why
      VCC5V / VINThe sensor needs 5 V; at 3.3 V it is unreliable
      TRIGGPIO510 µs pulse starts a measurement
      ECHOGPIO18 via 1 k / 2 k dividerECHO swings 5 V; ESP32 pins are 3.3 V max (5 V × 2/3 ≈ 3.3 V)
      GNDGNDCommon ground
      —GPIO2 (onboard LED)On while an alarm or a sensor fault is active
      • Sampling: 5 Hz (200 ms). The HC-SR04 needs ≥ 60 ms between pings for echoes to die out.
      • Timeout: 25 ms (~4.3 m). A missing echo returns −1, which the pipeline treats as invalid.
      • CPU: 80 MHz. One sample needs a few µs of maths, and the core sleeps in delay() between samples.
      • No sensor? The default build (SENSOR_SIMULATION=1) simulates one, with dropouts and ghost echoes.

      Data: raw, messy, realistic

      Training data has exactly the format the firmware prints in raw mode (timestamp_ms,distance_cm, −1 = no echo), so a real capture can replace a synthetic one 1:1. The synthetic generator models what goes wrong with a real ultrasonic sensor:

      Effects in generate_data.py

      • Measurement noise: Gaussian, with a different level per session (surface, angle, supply ripple)
      • Temperature drift: speed of sound = 331.3 + 0.606·T m/s, but the firmware assumes 343 m/s
      • Quantization: pulseIn() returns whole µs (0.017 cm steps)
      • Dropped echoes: −1 timeouts, single and in bursts, more frequent at long range
      • Ghost echoes: multipath double-bounce (2× distance), side reflectors, random junk
      • Blind zone / over-range: ringing gives < 2 cm, far targets give > 400 cm
      • Timing: loop jitter, serial stalls, lost lines
      • Contamination: "normal" sessions include someone reaching into the beam, as real ones do

      On-device cleaning

      Four steps run on the ESP32 before the model sees anything. The parameters are defined once in pipeline.py and generated into model_data.h, so device and training cannot drift apart.

        Why a Hampel filter, not a median filter

        • raw reading
        • Hampel-7 (used)
        • median-5 (rejected)

        A median filter wider than the vibration period cancels the vibration, because the samples walk around the sine and the median sits in the middle. In testing, a ±3 cm vibration at 1.7 Hz was detected 21 % of the time with median-5 and 99 % with Hampel-7. The Hampel filter only replaces a reading that is an outlier relative to the spread of its neighbours.

        Training on the PC

        train.py runs six steps in about 40 s on a CPU. The model is unsupervised: it only ever sees normal data.

        1. Load raw captures and report their problems (table above).
        2. On-device cleaning: the exact Python mirror of the firmware turns every raw reading into 4 features.
        3. Offline contamination removal (PC only): rows whose distance leaves the session's robust baseline (median ± 6·MAD, min 2 cm) are dropped, along with neighbouring rows whose feature window overlaps the event.
        4. Train the 4-8-2-8-4 autoencoder (Adam, MSE loss, early stopping). Chronological 80/20 split per recording: no shuffled leakage between train and validation.
        5. Threshold = 99.9th percentile of the reconstruction error on normal data. Normal error is heavy-tailed, and mean + 3σ gave tens of false alarms per hour.
        6. Evaluate the complete device logic per anomaly event, then export the C headers, re-check them against Keras, and copy them into firmware/include.

        The model: a 472-byte autoencoder

        No TFLite Micro runtime (~300 KB). The Keras weights are exported as C arrays, and the forward pass is a templated dense<IN,OUT,ACT> function, so the compiler checks every shape and unrolls the loops.

        template <int IN, int OUT, Activation ACT>
inline void dense(const float (&in)[IN],
                  const float (&W)[IN][OUT], const float (&B)[OUT],
                  float (&out)[OUT]) {
    for (int j = 0; j < OUT; ++j) {
        float sum = B[j];
        for (int i = 0; i < IN; ++i) sum += in[i] * W[i][j];
        out[j] = (ACT == RELU) ? relu(sum) : sigmoid(sum);
    }
}

        Single-precision floats only (the ESP32 FPU has no double support). The browser copy rounds to float32 the same way.

        Firmware

        Arduino framework on PlatformIO. Only main.cpp and sensor.cpp touch Arduino APIs, and the cleaning and inference files are plain C++, so they also compile on a PC for verification.

        The 200 ms loop (main.cpp)

        1. Sleep in delay() until the next slot. The FreeRTOS idle task halts the core instead of busy-waiting.
        2. Acquire one raw reading: SensorManager::read() (HC-SR04 or simulator).
        3. Clean: SignalPreprocessor::push() returns features, or invalid. 5 invalid in a row = sensor fault.
        4. Infer: InferenceEngine::run() (timed with micros()) gives the MSE and whether it is over the threshold.
        5. Decide: AlarmFilter raises the alarm after 3 anomalous samples in a row and clears it after 3 normal ones. LED = alarm OR fault.
        6. Log a CSV line. Every 60 s a # summary: readings, invalid, spikes removed, alarms, faults, inference µs, power estimate, free heap.

        Verification: one pipeline, three languages

        If the device cleaned data even slightly differently from training, the model would be scoring data it never learned. So the logic is mirrored and checked automatically.

        pipeline.pySource of truth for every parameter. Used by training.
        verify_firmware.pyg++ builds preprocess.cpp + inference.cpp with host_check.cpp, replays the test captures, compares every sample
        preprocess.cpp · inference.cppWhat runs on the ESP32.
        verify_web.pyNode runs pipeline.js on the same captures. Filtered values identical, MSE within float32 rounding, 0 LED mismatches
        pipeline.jsWhat runs on this page.

        train.py also checks that its C-style forward pass matches Keras, and that the exported headers round-trip, before copying them to the firmware.

        Limits, stated honestly

        • All numbers come from synthetic data. Real deployments should retrain on their own captures.
        • A 5 Hz sensor only sees vibration through aliasing. Vibration at an exact multiple of 5 Hz is invisible.
        • A sensor stuck on a constant valid value looks like a perfectly still object.
        • The 19 µs inference benchmark predates the current pipeline and the 80 MHz default. The firmware prints a fresh measurement every 60 s.
